# Context Management

This document explains how Mistral Vibe manages context across the main agent,
subagents, tools, scratchpad files, session logs, compaction, and persistent
configuration.

## Context Layers

Vibe has multiple kinds of context. They are related, but they are not the same
thing:

| Layer | What It Contains | Lifetime |
| --- | --- | --- |
| Conversation context | `LLMMessage` history sent to the model | Current session, compacted or resumed |
| Runtime context | active config, agent profile, tool manager, callbacks, session paths | Current `AgentLoop` instance |
| Tool context | `InvokeContext` passed into each tool call | One tool invocation |
| Scratchpad context | temporary files in a session-scoped directory | Current process/session temp lifetime |
| Persistent context | session logs, config, skills, tools, agents, prompts, `AGENTS.md` | Filesystem |
| Project context | cwd, git status, project instructions | Rebuilt into the system prompt |

The main runtime object is `AgentLoop`. It owns the message list, active agent
profile, tool manager, skill manager, middleware, session logger, telemetry
client, rewind manager, and optional scratchpad directory.

## Conversation Context

Conversation context is stored in `MessageList`, a sequence of `LLMMessage`
objects. Messages have roles:

- `system`: generated system prompt
- `user`: user prompts and injected runtime messages
- `assistant`: model responses, reasoning, and tool calls
- `tool`: tool results returned to the model

On every LLM call, `AgentLoop._chat()` or `_chat_streaming()` sends the current
`self.messages` plus available tool schemas to the backend.

```text
system prompt
user request
assistant tool call
tool result
assistant follow-up tool call
tool result
assistant final answer
```

Tool results are part of conversation context. After a tool finishes,
`AgentLoop._handle_tool_response()` creates a `role="tool"` message. The next
LLM turn can then reason over that observation.

## Runtime Context

Runtime context lives on the `AgentLoop` instance:

- `_base_config`: the loaded base configuration
- `agent_manager`: active profile and profile-derived config overlay
- `tool_manager`: builtin, custom, MCP, and connector tools
- `skill_manager`: available skills
- `backend`: active LLM backend
- `middleware_pipeline`: pre-turn controls
- `session_logger`: local persistence
- `rewind_manager`: checkpoints and file snapshots
- `scratchpad_dir`: session-scoped temporary workspace
- `approval_callback`: UI or ACP approval bridge
- `user_input_callback`: structured user input bridge
- `_sampling_handler`: MCP sampling bridge

The active runtime config is `agent_manager.config`, not just the raw base
config. Agent profiles can overlay tool permissions, enabled tools, active
model, system prompt id, and other settings.

## Tool Invocation Context

Each tool call receives an `InvokeContext`. The agent loop constructs it at tool
execution time and passes operational handles into the tool:

- `tool_call_id`
- `approval_callback`
- `agent_manager`
- `user_input_callback`
- `sampling_callback`
- `session_dir`
- `entrypoint_metadata`
- `plan_file_path`
- `switch_agent_callback`
- `skill_manager`
- `scratchpad_dir`

This keeps tool APIs explicit. Tools do not reach into the full `AgentLoop`;
they receive only the handles they are allowed to use.

Examples:

- `task` uses `agent_manager`, `session_dir`, `entrypoint_metadata`,
  `approval_callback`, and `scratchpad_dir`.
- `exit_plan_mode` uses `agent_manager`, `user_input_callback`,
  `plan_file_path`, and `switch_agent_callback`.
- MCP tools use `sampling_callback` when a server requests sampling.

## System Prompt Context

The system prompt is generated by `get_universal_system_prompt()`. It combines:

- configured base system prompt
- headless-mode instructions
- commit signature instructions
- active model name
- OS and shell details
- per-tool prompt files
- available skills
- available subagents
- scratchpad directory instructions
- project context and git status
- user-level `AGENTS.md`
- trusted project `AGENTS.md`

The system prompt is rebuilt when:

- deferred MCP or connector discovery completes
- tools, skills, or config reload
- the active agent profile changes
- a new `AgentLoop` is created

On resume, Vibe loads non-system messages from disk and builds a fresh system
prompt from current runtime state. This lets old sessions pick up changed tools,
skills, config, and project instructions.

## Main Agent To Subagent Context Flow

Subagents intentionally do not inherit the full parent message list. The `task`
tool creates a new nested `AgentLoop`, then sends a new task prompt to that
loop.

Shared from parent to subagent:

- selected subagent name
- delegated task text
- parent approval callback
- entrypoint metadata
- parent session logging location
- scratchpad path

Not shared:

- full parent message history
- parent assistant reasoning trace
- parent accumulated tool observations
- parent rewind checkpoints

Returned to parent:

- final accumulated subagent assistant text
- completion flag
- assistant turn count
- progress messages for subagent tool results

This keeps the parent context compact while allowing the subagent to do detailed
exploration independently.

## Scratchpad Context

Primary sessions initialize a scratchpad directory with:

```text
tempfile.mkdtemp(prefix="vibe-scratchpad-<short-session-id>-")
```

The active scratchpads are tracked in process memory by session id. File tools
call `is_scratchpad_path()` to check whether a path resolves inside any active
scratchpad.

Scratchpad rules:

- It is a temporary directory outside the repository.
- It is auto-allowed for file tools.
- It is included in the system prompt for the main agent.
- It is injected into subagent task text.
- It is intended for drafts, temporary scripts, intermediate outputs, and
  scratch summaries.
- It is not the same as persistent session storage.

Scratchpad files may disappear with the OS temp lifecycle or process lifetime.
Important information should be returned in messages or written to project files
with approval if it needs to survive.

## Session Logging

Session logging stores the durable conversation trace. `SessionLogger` creates a
session directory under `session_logging.save_dir`.

Folder naming:

```text
<session_prefix>_<YYYYMMDD_HHMMSS>_<short-session-id>/
```

Files:

```text
messages.jsonl
meta.json
```

`messages.jsonl` is append-only. It stores non-system messages:

- user messages
- assistant messages
- tool messages

`meta.json` stores metadata and is written atomically with a temp file plus
`os.replace`.

Metadata includes:

- session id
- parent session id
- start/end time
- git commit and branch
- working directory
- username
- title
- stats
- total message count
- available tool schemas
- config snapshot
- active agent profile
- system prompt snapshot
- scheduled loops

The logger appends only new messages by comparing the previous
`total_messages` count from `meta.json` with the current non-system message
count.

## Subagent Logging

When a subagent runs through the `task` tool and the parent has session logging,
the child session logger writes under:

```text
<parent-session-dir>/agents/
```

The subagent's `session_prefix` is the subagent name, so a delegated `explore`
run creates a folder like:

```text
<parent-session-dir>/agents/explore_<timestamp>_<short-session-id>/
  messages.jsonl
  meta.json
```

The parent session gets only the `TaskResult` as a tool observation. The detailed
subagent conversation remains in the nested log.

## Resume And Fork

Resume uses `SessionLoader`:

1. Find a session directory by id or latest session.
2. Validate `meta.json` and `messages.jsonl`.
3. Load non-system messages from `messages.jsonl`.
4. Create a new `AgentLoop`.
5. Extend the new loop's messages with loaded non-system messages.
6. Resume the existing session logger path.

Fork creates a new `AgentLoop` with copied base config and selected message
history. It assigns a new session id with the source session id as parent.

Resume keeps durable conversation context. Fork creates a related but separate
branch of conversation context.

## Compaction

Compaction is the context-window pressure release valve. The
`AutoCompactMiddleware` checks `stats.context_tokens` against the active model's
`auto_compact_threshold`.

When compaction runs:

1. Save current session.
2. Add the compaction utility prompt.
3. Call the compaction model, or active model if none is configured.
4. Extract the summary.
5. Reset messages to:

```text
system message
summary-as-user-message
```

6. Reset the session id and link the old one as parent.
7. Count tokens for the compacted context.
8. Save the compacted session.

Compaction intentionally loses low-level detail in exchange for keeping the
session usable within the model context window.

## Rewind Context

`RewindManager` adds another context dimension: file state. Before each user
turn, the agent creates a checkpoint. Editing tools can provide pre-write file
snapshots through `get_file_snapshot()`.

When rewinding, Vibe can:

- save the current session
- truncate messages back to a selected user message
- optionally restore files from snapshots
- reset to a new child session id

Conversation context and filesystem context can therefore be moved backward
together when supported by snapshots.

## Persistent Configuration Context

Long-lived context comes from the harness files manager:

- `VIBE_HOME/config.toml`
- `VIBE_HOME/AGENTS.md`
- `VIBE_HOME/tools/`
- `VIBE_HOME/skills/`
- `VIBE_HOME/agents/`
- `VIBE_HOME/prompts/`
- trusted project `.vibe/config.toml`
- trusted project `.vibe/tools/`
- trusted project `.vibe/skills/`
- trusted project `.vibe/agents/`
- trusted project `.vibe/prompts/`
- trusted project `AGENTS.md` files

Project context is loaded only when project sources are enabled and the working
directory is trusted. This protects users from automatically executing or
loading project-local agent configuration from untrusted folders.

## Context Flow Summary

```text
startup
  -> load config and trusted project/user files
  -> discover agents, tools, skills
  -> build system prompt
  -> create MessageList(system)

user turn
  -> append user message
  -> middleware may inject messages, compact, or stop
  -> LLM receives MessageList + tool schemas
  -> assistant message appended
  -> tool calls parsed and validated
  -> tools receive InvokeContext
  -> tool results appended as tool messages
  -> loop repeats while tool messages are present
  -> session logger persists non-system messages + metadata

subagent task
  -> create fresh subagent AgentLoop
  -> pass task text + scratchpad note + callbacks
  -> subagent logs separately
  -> parent receives only TaskResult and progress

resume
  -> load non-system messages
  -> regenerate current system prompt
  -> continue same session directory
```

## Key Takeaways

- The main context sent to the LLM is `MessageList`.
- Tools extend context by returning observations as `role="tool"` messages.
- Subagents are context-isolated nested loops.
- Scratchpad is a shared temporary filesystem workspace, not durable storage.
- Session logs are durable local storage for replay and resume.
- Config, skills, tools, agents, prompts, and `AGENTS.md` are persistent context
  inputs that shape new and resumed sessions.
- Compaction summarizes message context when the context window gets too large.
